`fn_worker_run_finalize_cycle` selects every battle in `voting` or `scoring` whose
`voting_closes_at` has passed. Four demo battles were seeded with hardcoded absolute
dates, which were accurate when written and became finalize candidates as soon as
wall-clock time overtook them — no commit required.

The consequence surfaced far from the cause. The finalize end-to-end test asserts that
the first sweep finalizes exactly one battle, the one it creates itself; the decayed seed
rows were counted alongside it, so the test failed on pull requests that had not touched
a seed file, and would have degraded further as more dates passed.

Each window is now relative, preserving its original four-day span and the ordering the
seeds had among themselves. Battles left in a terminal state keep their historical dates,
since the finalize predicate never re-evaluates them.

A new invariant seed runs last and fails the load if any battle is left in `voting` or
`scoring` past its own deadline, naming the offending rows. Because the defining property
of this bug was that nothing surfaced it, the check is asserted at the source. It is
intentionally not gated on the environment setting the older CI guard uses, since
`supabase db reset` does not apply that setting and is the path CI takes.
