  Creating a battle with a lens and shared parameter values looked fully wired — the CLI accepted --lens-id, the schema stored the parameter snapshot, and the contender was recorded against a lens version — but the worker ignored all of it and sent the battle's raw task prompt to the model. Every lens-bound battle ran without its lens. Contenders now execute the assigned lens version with its [[Parameter]] tokens filled in from the battle's shared inputs, so all contenders see the identical hydrated prompt the feature always described.

  Two latent faults that would have surfaced as soon as anyone relied on this are fixed alongside it: the lens renderer could never read a lens version at all (the table enforces row-level security in a way that blocked even the privileged path), and the worker's job-claim entry point declared one of its columns with the wrong type, which made the call fail outright.

The worker called the body-based render overload with the battle's own `task_prompt` on
both sides — rendering it against itself with a single `{prompt}` input, which is a no-op
unless `task_prompt` literally contains `[[prompt]]`. The lens version bound to the
contender was never fetched and `shared_input_snapshot` was never passed.

A version-based renderer already existed and was already `service_role`-only, so the
worker was simply calling the wrong overload. That renderer could not have worked either:
it reads `lenses.versions`, which has `FORCE ROW LEVEL SECURITY`, and its wrapper never
set `row_security TO off` — so the read returned nothing even for the definer. Because a
function's `SET` clause is inherited by nested calls, setting it on the worker-only
wrapper is sufficient; the shared renderer and its grants are untouched and the bypass
stays scoped to an entry point no end user can reach.

Rendering by version id rather than by raw body also keeps legacy `[[:uuid]]` token
rewriting and required-parameter enforcement in one place instead of degrading to a naive
substitution inside the worker.

The native and Chainabit execution paths held byte-identical copies of this logic, which
is how the same defect existed twice; they now share one prompt-resolution owner. The
worker test that asserted the old behaviour is restated rather than deleted, since that
assertion described the bug.
