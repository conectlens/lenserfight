userImpact: |
  Starting a workflow from the builder used to make that browser tab the run's only executor. Closing the tab abandoned the run silently — no error, no way to resume — and it sat pending forever. The CLI hit the same wall from the other side, polling for a terminal status that could never arrive. Manual runs now go to the background worker by default, so they finish whether or not the tab stays open, and reopening /workflows/:id/run/:runId reattaches to a run already in flight. Runs that must stay in the browser (BYOK, where the API key only exists client-side) keep a heartbeat, and anything abandoned is retired instead of hanging.

  Also closes an authorization gap: fn_mcp_workflow_run_start ran as SECURITY DEFINER and was granted to any authenticated caller with no ownership check, so a signed-in user could start a run against any workflow UUID — including private workflows belonging to someone else — and read the output back through fn_mcp_workflow_run_status. It now enforces ownership and visibility, the kill switch, rate limiting, and idempotency.

  Retrying a run can no longer be picked up twice, recovery no longer re-bills already-completed nodes, and worker-executed runs stream token partials so routing a run server-side does not downgrade the builder to a single status jump.

`trigger_mode` conflated two independent facts: who triggered a run and who executes it.
The only server-side claimer filtered `trigger_mode IN ('schedule','api')`, so a run
started by a human — which fell through to the column default `'manual'` — was claimable
by nobody. Every new trigger mode had to be remembered in that `IN`-list, and it was
missed twice: first for `'api'`, then for `'manual'`.

The fix splits the axes. `lenses.workflow_runs.executor` records who runs a workflow and
is the only column a claimer inspects, so adding a trigger mode can no longer strand
runs. It defaults to `worker`; `client` is reserved for browser-executed BYOK runs, whose
key is physically unreachable from a worker. Durability is layered on top: route to the
worker, heartbeat and adopt, then reap-and-fail as a backstop.

Two pgTAP tests asserted that the claimer skips `trigger_mode='manual'`. That assertion
was the bug, so both are restated on the executor axis rather than deleted.

Both migrations are additive. Historical `manual` rows backfill to `'client'` because
they were browser-driven by construction; pre-existing orphans stay `'client'` on purpose,
since the worker cannot know their funding source and adopting one could re-run a
local-BYOK graph it has no key for. The reaper retires those instead, which is what
clears the stuck runs. Rollback is a straight revert of both migrations — `executor` is
read only by the claim and reap functions, and no data is lost.
